# Обґрунтування стеку та стратегія тестування

## 1. Вибір мови програмування

**Обрана мова: Python.**

Стек проєкту — TS на фронті, Python на бекенді. Раніше в цьому документі я обирав
TypeScript (щоб E2E і API тести жили в одному Playwright-ранері та фронтенд міг їх
рев'ювити), і це теж був чесний варіант. Але коли йдеться саме про Python-бекенд —
природніше писати тести тою ж мовою, якою написаний застосунок, і ось чому:

- **Бекенд-розробники читають і пишуть тести без перемикання контексту.** Вони можуть
  рев'ювити API-тести так само вільно, як власний код, а якщо в проєкті вже є pydantic-
  моделі — ті самі моделі (або їх копії) можна перевикористати як схеми відповідей замість
  того, щоб дублювати контракт окремою мовою.
- **pytest покриває всі три рівні одним інструментом.** `pytest-playwright` дає E2E,
  `requests` — API, звичайні функції з `assert` — unit. Один test runner, один конфіг
  (`pytest.ini`), один звіт (Allure) — та сама перевага "все в одному місці", що я
  раніше приписував Playwright/TS, тут просто дістається Python-екосистемі.
- **Playwright для Python — не другорядний порт.** Той самий рушій (Chromium/Firefox/
  WebKit), той самий API 1:1 з JS-версією, offiційно підтримується Microsoft нарівні з
  JS/Java/.NET біндингами. Тобто вибір Python тут не коштує нічого в якості E2E-шару.

**Компроміс, який усвідомлюю:** фронтенд-команда (TS) вже не читає тести з ходу так
легко, як читала б TS-версію. Пом'якшую це тим, що API-схеми (`pydantic`) і Page Object-
класи мають прості, явно названі методи з докстрінгами — фронтендер, який хоче зрозуміти
що саме перевіряється в E2E, читає їх майже як псевдокод, навіть не знаючи Python
детально. Якби в проєкті переважна більшість тестів була E2E проти складного UI
(багато кастомних React-хуків, які frontend-команда мала б рев'ювити щодня), я б
залишив TypeScript — тут переважило вирівнювання з бекендом.

### Інструменти

| Рівень | Інструмент | Чому |
|---|---|---|
| E2E (UI) | pytest-playwright | Auto-wait, ізоляція браузерних контекстів, той самий рушій що й у Playwright/JS |
| API | `requests` + `pydantic` | `requests` — найпростіший спосіб робити HTTP-виклики в Python; pydantic-моделі валідують схему відповіді і дають зрозумілу помилку, якщо контракт зламався |
| Unit / integration | pytest (`assert`, `pytest.mark.parametrize`) | Стандарт де-факто в Python-екосистемі, не потребує додаткових бібліотек для базових перевірок |
| Звітність | `allure-pytest` + Allure CLI | Один формат звіту для всіх трьох рівнів (unit/API/E2E результати з різних кроків CI зливаються в один звіт), історія прогонів між білдами, групування по фічах/severity — детальніше нижче |

Unit-рівень (`tests/unit/`) тут покриває утиліти самого тест-фреймворку (завантажувач
конфігурації середовища, генератори унікальних тестових даних, класифікатори HTTP-
статусів) — реального прикладного коду в цьому репозиторії немає, оскільки тестуємо
публічні демо-сервіси. На реальному проєкті цей рівень — це unit-тести самого бекенду
(pytest над чистими функціями/сервісами), а не тести навколо тестового фреймворку.

### Інші компроміси

- **pytest-playwright vs Selenium/Selenium+unittest:** Playwright дає авто-очікування
  елементів і набагато менше "flaky" тестів з коробки, ніж класичний Selenium; ціна —
  трохи менша інерція/legacy-документація порівняно з Selenium, який старіший і його
  простіше "нагуглити" для рідкісних кейсів.
- **pytest-html vs Allure:** починав з `pytest-html` (один пакет, нуль інфраструктури,
  самодостатній `.html`-файл) саме тому, що Allure вимагає Java-рантайм і окремий крок
  `allure generate`. Перейшов на Allure, бо для цього завдання явно попросили його —
  і оскільки в CI (ubuntu-latest) Java вже стоїть за замовчуванням, а сам Allure CLI
  ставиться одним `npm install -g allure-commandline` (Node теж є з коробки), реальна
  ціна цього переходу виявилась мінімальною. Натомість Allure дає те, чого pytest-html
  не мав: результати unit/API/E2E кроків з CI зливаються в один звіт (`--alluredir` не
  перезаписує, а дописує), є групування по фічах через `@allure.feature`/`@allure.story`,
  видно severity й історію прогонів між білдами. Локально звіт — не один файл, а
  папка (`allure generate` розкладає статику + JSON), це найпомітніший мінус проти
  `pytest-html` для швидкого перегляду без сервера.
- **dummyjson.com не зберігає створені ресурси** (POST повертає echo + згенерований id,
  але даних у себе не лишає — задокументована поведінка мок-API; той самий досвід був і
  з reqres.in, який до того ж тепер вимагає реєстрації й власного `x-api-key` для будь-
  якого запиту — перевірив напряму, без ключа все повертає 401). Тому CRUD-chain тест
  (створення + перевірка, що ресурс з'явився) підняв проти локального Flask-застосунку
  (`tests/api/fixtures/fixture_server.py`), що стартує/гаситься автоматично через
  pytest-фікстуру `crud_api_server` (session-scope). Це чесніше, ніж вдавати, що
  перевірка відбулась, коли насправді дані нікуди не зберігаються. Авторизація, список
  ресурсів і схема відповіді й далі тестуються проти реального dummyjson.com.
- **Конфігурація середовищ читається без мутації `os.environ`.** `config/env.py` парсить
  потрібний `.env`-файл напряму (`dotenv_values`), а не через `load_dotenv()`, який записує
  значення в глобальний `os.environ`. У TS-версії цього документа була помилка саме на
  цьому: `dotenv.config({ override: false })` не перезаписувала вже виставлені змінні при
  повторному виклику з іншим `TEST_ENV` у тому самому процесі (спливло в unit-тестах).
  У Python-версії такого класу бага вже структурно немає — конфіг завжди читається з
  самого файлу, а не з мутованого глобального стану.

## 2. Стратегія тест-покриття

**З чого почав би покриття на новому проєкті.** Спершу — API-рівень для критичних
бізнес-потоків (авторизація, основні CRUD-операції). Це найдешевше і найстабільніше
покриття: запити швидкі, немає UI-флейків, легко ганяти в CI на кожен PR. Зверху —
тонкий шар E2E-смоук-тестів на 3-5 найкритичніших користувацьких сценаріїв (логін,
головний happy path), а не спроба покрити E2E все підряд. Unit-тести пишуться паралельно
з самим кодом бекенду, у міру його появи — по суті вони мають бути найбільшим шаром
(класична піраміда: багато unit, середньо API/integration, мало E2E).
